Ah, got it! That makes total sense—if SAP returns the same invoice number that we already have stored in OpexNOW, we need to inspect the status of our local existing invoice to determine what actually happened:

Active Local Invoice (Not Voided/Canceled): It was already created and synced properly. Let the user know it's already synced.

Voided/Canceled Local Invoice: The delivery was unlocked/released for re-billing in OpexNOW, but SAP is still returning the old voided invoice number (meaning a new BC billing document hasn't been generated in SAP yet). Tell the user to generate the new billing in SAP first.

TASK: Differentiate Active vs Voided Duplicate Invoice Responses in BC Delivery Sync
Please update DeliveriesController.cs in amtemeterai.Api to handle duplicate invoice numbers returned by SAP based on the local status of the existing invoice record.

PROBLEM
When syncing a delivery, SAP may return an invoice number that already exists in PostgreSQL (IX_Invoices_InvoiceNumber). Currently, attempting to save this causes a DbUpdateException (Postgres 23505 duplicate key).

We need to check the status of the local invoice record in _db.Invoices before trying to save, and handle the two scenarios accordingly.

REQUIREMENT
In DeliveriesController.cs inside CreateSapInvoice (or the handler processing the SAP response payload):

Lookup Existing Invoice in Local DB:
When SAP returns sapResponse.SapInvoiceNumber, query _db.Invoices for a record matching that invoice number.

Condition 1: Existing Invoice is ACTIVE (Not Voided / Not Canceled)

If an invoice with SapInvoiceNumber exists and its status is not Voided or Canceled:

Do NOT insert a new record into _db.Invoices.

Return 200 OK or 400 Bad Request with message: "Invoice already synced."

Condition 2: Existing Invoice is VOIDED or CANCELED

If an invoice with SapInvoiceNumber exists but its local status is Voided or Canceled:

Do NOT insert a new record into _db.Invoices (since SAP is still returning the old voided invoice number).

Return 400 Bad Request with message: "Please generate billing in SAP first."

IMPLEMENTATION CODE
C#
// 1. Fetch existing local invoice by SAP invoice number
var existingInvoice = await _db.Invoices
    .FirstOrDefaultAsync(i => i.InvoiceNumber == sapResponse.SapInvoiceNumber);

if (existingInvoice != null)
{
    bool isVoidedOrCanceled = existingInvoice.Status == Invoice.InvoiceStatus.Voided 
                           || existingInvoice.Status == Invoice.InvoiceStatus.Canceled;

    // Condition 2: Invoice exists locally but was Voided/Canceled (SAP hasn't created a new billing yet)
    if (isVoidedOrCanceled)
    {
        _logger.LogWarning("Sync blocked for Delivery {DeliveryNumber}: SAP returned voided invoice {InvoiceNumber}.", 
            deliveryNumber, sapResponse.SapInvoiceNumber);

        return BadRequest(new
        {
            success = false,
            message = "Please generate billing in SAP first."
        });
    }

    // Condition 1: Invoice exists locally and is Active
    return Ok(new
    {
        success = true,
        message = "Invoice already synced.",
        invoiceNumber = existingInvoice.InvoiceNumber,
        billingDate = existingInvoice.InvoicedDate
    });
}

// Proceed to save new invoice if existingInvoice == null...
ACCEPTANCE CRITERIA
If SAP returns an invoice number that is active in OpexNOW, the API returns "Invoice already synced." without attempting a duplicate DB insert.

If SAP returns an invoice number that was voided/canceled in OpexNOW, the API returns "Please generate billing in SAP first." without attempting a duplicate DB insert.

Completely eliminates DbUpdateException / IX_Invoices_InvoiceNumber constraint errors.
